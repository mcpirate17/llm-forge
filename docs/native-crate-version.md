# Native candidate crate-version check

`forge candidate crate-version --repo SNAPSHOT --base BASE_OID --tree TREE_OID [--execute] -- FILE...` checks captured Cargo production inputs and version discipline. Without `--execute`, it reports the bound plan only; with it, findings determine status 1, a clean evaluated result is 0, and incomplete input/evaluation is 2. `forge candidate crate-version --tool-version` reports the native evaluator identity without requiring Git context or installed metadata.

The command consumes the exact candidate snapshot and full base/tree object IDs supplied by the candidate stage. It selects changed captured paths, reads manifests and relevant source/base blobs, attributes production inputs to the deepest Cargo package, ignores manifest-only changes and test/bench/example directories, and compares source after Rust-aware `#[cfg(test)]` removal. Malformed/unresolvable manifests, missing package names and inherited versions remain explicit findings; source changes reaching a shipped artifact require a literal package version change. Deleted build inputs and both endpoints of selected renames are included, so moving production code into tests or another crate still checks the old package. Copies do not imply source deletion. The version comparison requires unequal strings; it does not enforce monotonic releases or establish cache freshness. This is a version-discipline comparison, not proof of which compiled artifact is installed or loaded.

Installed-version drift is evaluated only against operator-selected Python distribution metadata. `FORGE_CRATE_INSTALLED_ROOTS` must be a JSON array of ordered absolute canonical roots; `[]` explicitly declares that no installed distributions are in scope, while a missing variable is an error. Roots must be owned by root or the current UID and not group/other writable. Metadata files must be regular, singly linked and safely owned; symlinked/noncanonical paths are refused. Only `Name` and `Version` records for packages named by captured Cargo manifests are selected. The first root containing a package wins; duplicate matching records within one root are ambiguous and fail closed. Selected metadata bytes and root/file identities are held and rechecked, including selection, before returning. This binds the metadata comparison, but does not prove an installed binary loaded those files.

Bounds: 1–4096 selected change paths and at most 4096 endpoints after rename expansion; 4096 manifests/records; 1 MiB per captured source/base/manifest or metadata file; 32 MiB aggregate candidate evidence and separately 32 MiB selected metadata; at most 32 roots and 32768 directory entries per root; 4096 findings and 32 MiB encoded output. Metadata-root JSON is limited to 128 KiB. Exceeding a limit is incomplete, not a clean result. The parent candidate stage provides the execution isolation boundary; direct CLI use does not create an independent sandbox. Each nonempty installed root also requires an explicit parent-stage `read_only` grant; setting the environment variable alone grants no filesystem access.

The native policy entry is a command (`cache=false`, `run_on_deletions=true`), so host policies that still describe `crate-version` as a Python builtin must migrate to the native command form. The version probe is `forge candidate crate-version --tool-version`. The Python evaluator, builtin dispatcher and compatibility target are deleted.

Focused release validation passed 10 evaluator tests, five Rust projection tests, eight metadata-reader tests, 12 CLI tests and three explicitly enabled sandbox Stage tests. Coverage includes renamed and copied inputs, deleted production files, nested ownership, malformed Rust and manifests, installed-root selection and drift, captured Git bytes, resource verification and cleanup. The CLI cases use the freshly compiled native executable with interpreter paths forbidden. Stage tests additionally require `FORGE_TEST_CGROUP_PARENT` to name a delegated cgroup; the metadata case grants its exact external root read access and checks the returned SHA-256.

The [current-only evaluator benchmark](../research/performance/native-crate-version-20261101.json) records source and executable hashes, workload hashes and sampling details. Median sample means were 18.773 µs for one production-changing crate and 2.255 ms for 128 crates; test-only changes measured 16.453 µs and 2.029 ms. These warm synthetic measurements include AST/TOML processing and result allocation/destruction, but exclude input JSON parsing, Git, filesystem, CLI startup and sandbox work. They establish no baseline speedup or end-to-end dispatch latency.

Remaining evidence boundary: validating that an installed binary actually loaded the captured distribution, and any stronger artifact identity/attestation, are separate capabilities and are not inferred from the metadata roots.
